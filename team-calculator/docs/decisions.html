Timeline

Eight days, six passes, one direction.

Each pass answered a question the previous one raised. The first version proved the reconciliation math; the last one answered a CFO's objections. Hover a marker for what shipped.

OCT 12 TO 13 · GROUNDWORK

The site that would host it

Three redesign concepts for jaybeatty.com in black, purple and green. Jay chose Scoreboard. That palette, type and layout became the calculator's identity, which is why the tool reads as part of the site rather than a widget bolted on.

OCT 15 TO 16 · THE MODEL

From rules to a working engine

Jay said GO. Version one implemented the published reconciliation order from the CMS PY1 target price workbook and fact sheets. The next day added the levers module, because Jay asked whether post-discharge care and complications belonged, and the evening added service-line tabs and five case hospitals on real 2024 volumes.

OCT 18 TO 19 · THE DATA AND THE CRITIQUE

Real data, then hard questions

Jay asked what public data had not been used. Thirteen datasets later, every participant prefills. Then he asked for a CFO's objections, sixteen of them, and had all sixteen fixed in priority order, followed by a margin-context line prompted by a Kaufman Hall report he shared.

The model

What the engine does with a hospital.

Two layers. The reconciliation engine applies the published CMS rules to whatever inputs it is given. The prefill layer turns a hospital's public record into those inputs, and labels each one as real, derived or assumed.

Not yet checkedneeds data the tool does not have

Against a real reconciliation. No hospital's PY1 reconciliation report exists yet; the first arrives in 2027. Until then the engine is validated against CMS examples, not CMS outcomes.

The prefilled spend. It is derived from all-condition spending patterns. The only test is a hospital comparing it with its own CMS baseline report, which is why the field is labeled and the badge asks for the real number.

The risk-multiplier seed. A labeled proxy. CMS's target price reports will show how far off it is; the break-even and the ±0.06 band exist so the answer survives being wrong.

Automated tests. The checks run in the browser. A test file a reviewer can run from the command line is on the roadmap below.

What comes next

From a calculator to a product, in order.

A twenty-year healthcare software developer's verdict on the tool was "decent free tool, would never pay for it." That review is kept here because it is the roadmap. The single-file design was the right call for a portfolio piece and the wrong starting point for a product; everything below needs a backend.

1 · OWN THE HOSPITAL'S DATA

Ingest the CMS baseline and claims files

Every participant receives its baseline episode file, target price report and quarterly claims feed. Reading those replaces the derived spend with actual episodes and makes episode construction, exclusions and overlaps real instead of modeled.

2 · MAKE IT A RECORD

Accounts, saved scenarios, Excel export

Scenarios persist, compare across months, carry an audit trail, and export with formulas intact. A board pack a finance team can drop into its own workbook.

3 · USE THE ASSET ALREADY LOADED

Peer benchmarking across 721 hospitals

The dataset to rank any hospital's post-discharge spend, readmissions and quality against every other participant in its division is already in the file. Nobody is showing a CFO that view.

4 · ESTIMATE RISK PROPERLY

HCC-based risk multiplier from the hospital's own claims

CMS publishes enough of its methodology to replace the seeded proxy with a real estimate once the claims are in.

5 · SYSTEM VIEW

Roll up a dozen CCNs

Systems run TEAM across many hospitals. Side-by-side cases exist; a roll-up with shared assumptions does not.

6 · ENGINEERING HYGIENE

Tests, manifest, history

A command-line test file for the engine (done October 22: tests/engine.test.js, 22 checks run with node --test, after the math moved into a pure engine.js with no change in output), a data manifest with pull dates and row counts (the table above is its first draft), and a commit history that shows the iteration rather than a few large commits. The architecture note maps the build and draws version two.
